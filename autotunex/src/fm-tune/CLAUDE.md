## Architecture Overview

fm-tune is a Ray Tune-based HPO system for distributed LLM fine-tuning. The flow is:

```
main.py (CLI) → AutotuneOptimizer.fit() (HPO) → driver_*.py (training) → tune.report()
                                               ↓
                AutotuneOptimizer.fit_best_config() → driver_*.py (final training + model save)
```

### Core Pipeline

1. **main.py** — CLI entry point. Parses args, starts Ray cluster, creates `AutotuneOptimizer`, calls `fit()` then `fit_best_config()`.

2. **autotune/optimizer.py** — `AutotuneOptimizer` orchestrates HPO via Ray Tune. `setup_pipeline()` builds the param search space from YAML config. `fit()` runs HPO trials (a crashed sweep is NOT restored — rerun the job). `fit_best_config()` retrains with the best (or `--no_autotune` default) hyperparameters and persists the resolved config to `final_checkpoints/final_config.json`. `--resume_from_checkpoint` short-circuits `fit()` when a saved config + checkpoint exist there, loading the saved config and resuming final training from the last checkpoint (see `autotune.utils.has_resumable_final_checkpoint` / `load_final_config`).

3. **autotune/config.py** — `AutotuneConfig` loads YAML into four sections: `tune_config`, `training_config`, `training_rl_config`, `tuners_config`/`tuners_rl_config`.

4. **autotune/pipeline.py** — `AutotunePipeline` validates that tuning_algo + rl_algo combinations are legal.

5. **autotune/constants.py** — Maps tuning algorithm names to PEFT types, defines `AUTOTUNE_OFFLINE_RL` (dpo, kto) and `AUTOTUNE_ONLINE_RL` (ppo, grpo, dapo).

### Driver Selection (optimizer.py)

Drivers are selected based on `num_gpus_per_trial`, `rl_algo`, `train_implementation`, and `--backend`:

| GPUs | RL Algorithm | `train_implementation` | Driver |
|------|-------------|------------------------|--------|
| 1 | none (SFT/PEFT) | — | `driver_single.py` |
| 1 | dpo, kto | — | `driver_single_trl.py` |
| >1 | none (SFT/PEFT) | DeepSpeed | `driver_multi_hf_ds.py` |
| >1 | none (SFT/PEFT) | FSDP | `driver_multi_hf_fsdp.py` |
| >1 | dpo, kto | DeepSpeed | `driver_multi_trl_ds.py` |
| >1 | dpo, kto | FSDP | `driver_multi_trl_fsdp.py` |
| >1 | ppo, grpo, dapo | — (verl+FSDP) | `driver_multi_verl.py` (verl + vLLM) |

For >1 GPU SFT/DPO, `training_config.train_implementation` selects DeepSpeed vs
FSDP (the shipped `autotune*.yaml` configs default to `FSDP`; if the key is
absent the code in `optimizer.py` falls back to DeepSpeed / `"huggingface_ds"`).
The single-device MLX backend (`--backend mlx`) routes to `driver_single_mlx.py`
(see MLX routing below).

**MPS routing:** On Apple silicon, `autotune/device.py::detect_accelerator()` returns `mps` (precedence CUDA → MPS → CPU; override with `FMTUNE_DEVICE=cuda|mps|cpu`). `fit_best_config()` derives `multi_gpu` from `accel.supports_distributed` (`False` on MPS), so final training always routes to `driver_single.py` — never DeepSpeed/FSDP — regardless of `num_gpus_per_trial`. Ray can't schedule Metal as a resource, so HPO trials reserve `{"CPU": 1, "GPU": 0}` bundles and use the MPS device inside the trial process; correctness under concurrency comes from `apply_platform_guards` clamping `max_concurrent_trials` to 1, not from Ray GPU accounting. See `docs/MPS.md` for the full support matrix.

**MLX routing:** `--backend mlx` routes single-device SFT/LoRA/QLoRA to `driver_single_mlx.py` via `autotune/mlx_backend.py`; qlora → MLX 4-bit; output is MLX-native (not PEFT). See `docs/MPS.md`.

**Shadow Residual (`--tuning_algo sr`) routing:** SFT only, CUDA only, and **FSDP only** — `driver_single.py` (1 GPU) and `driver_multi_hf_fsdp.py` (>1 GPU, `train_implementation: FSDP`). The four drivers SR must never reach raise a clear `ValueError` on `tuning_algorithm == "sr"`: `driver_multi_hf_ds.py` (DeepSpeed) and the three TRL drivers (offline RL). Note the HPO/final asymmetry that the table above already implies — HPO trials with `num_gpus_per_trial: 1` run `driver_single.py`, while `fit_best_config()` sets `multi_gpu = accel.supports_distributed` (`True` on any CUDA box), so final training goes to the FSDP driver with `num_workers = num_gpus_per_trial * max_concurrent_trials`. Both SR paths are therefore exercised by a single `sr` run on CUDA.

### Driver Pattern

All drivers follow the same contract:

```python
def train_driver_*_gpu(config: Dict[str, Any]) -> Dict[str, Any]:
    # 1. Pop sections: training_config, training_rl_config, tuner_flags, tune_config
    # 2. Split sampled params: PEFT kwargs (tuner_flags[k]=True) vs Trainer kwargs (False)
    # 3. Load model, datasets, build trainer
    # 4. Train
    # 5. Report: tune.report({"loss": ..., "train_loss": ..., "done": True, ...})
```

Multi-GPU drivers (HF/TRL) use Ray Train's `TorchTrainer` wrapper. The verl driver uses `RayPPOTrainer` directly.

### Config System

YAML configs define hyperparameter search spaces. Each param has:
- `strategy` — sampling method (choice, uniform, loguniform)
- `values` — discrete choices or range bounds
- `default` — value used when `--no_autotune`
- `for_tuner` — where the value goes, not whether it is swept: `true` → PEFT adapter config (`peft_kwargs`, e.g. LoRA `r`), `false` → HF/TRL `TrainingArguments` (`train_kwargs`, e.g. `learning_rate`). Every param in a search space is sampled either way (`get_strategy` ignores the flag); to fix one, give it a single value. The verl driver ignores the flag and passes every sampled param to verl.

### Checkpointing Pattern

- All three HF SFT drivers (`driver_single.py`, `driver_multi_hf_ds.py`, `driver_multi_hf_fsdp.py`) resolve their save/eval strategy through one helper, `autotune/trainers/_checkpointing.py::resolve_checkpoint_strategy`, which also encodes HF's `load_best_model_at_end` preconditions. Change checkpointing behavior there, not per driver.
- The `steps_per_epoch` those strategies are sized in comes from `autotune/trainers/_steps.py::resolve_epoch_steps` and is in **optimizer** steps (micro-batches // `gradient_accumulation_steps`), matching what HF counts. All five SFT/TRL drivers share it; see the `max_steps` gotcha below for what computing it per driver cost.
- **HPO trials**: `save_strategy="epoch"`, `save_total_limit=1` (minimal, just enough for metrics reporting; the single-GPU driver passes `hpo_save_strategy="no"` and saves nothing, reading metrics from `trainer.state.log_history` instead). No best-model tracking — no model is persisted.
- **Final training**: `load_best_model_at_end=True`, `metric_for_best_model="eval_loss"`, `greater_is_better=False`, `save_total_limit=3`. `trainer.save_model()` therefore writes the **best** epoch, because `train()` reloads the best checkpoint before returning. A single-epoch run switches to a `steps` cadence (5× per epoch, `save_steps == eval_steps`) since one epoch boundary gives the best-model search nothing to choose between. `save_total_limit` rotation exempts the best checkpoint, so it survives even outside the newest 3.
- **verl driver**: Saves the last checkpoint via `_last_hf_model_dir()` (skips `global_step_*` dirs whose `actor/` verl's `max_actor_ckpt_to_keep` rotation deleted; no validation runs, so there is no reliable "best" to pick). `_InMemoryMetricsLogger` collects per-step metrics (both in `autotune/callbacks/verl_metrics.py`, verl/torch-free so they test on any platform). The in-memory logger also forwards each step to a `VerlStepReporter`, which writes one `training_metrics` row (`loss`=`actor/pg_loss`, `grad_norm`, `learning_rate`=`actor/lr`, rest in `extra`) and one `[AutoTune] verl step N: …` trial-log line.
- After model save, `checkpoint-*` dirs (or `global_step_*` for verl) are cleaned up
- **`--model_at_root`** (off by default; AutotuneX passes it): `main.py`'s `finally` calls `utils.promote_model_to_root()` only after a successful run — moves `<output_dir>/<model_name>/` (or `models/<model_name>/`) contents to `<output_dir>/` and deletes everything else, or moves it into `diagnostics/` with `--keep_diagnostics` / `FMTUNE_KEEP_DIAGNOSTICS=1`. Needed because granite.build uploads the whole `output_dir` as the HF repo.
- **Final-training resume**: `fit_best_config()` writes the resolved config to `final_checkpoints/final_config.json` before training. On success the whole `final_checkpoints/` dir (config + checkpoints) is removed; an interrupted run leaves both behind so a later `--resume_from_checkpoint` can read the config, skip HPO, and resume from the last `checkpoint-*`.

### verl Integration (driver_multi_verl.py)

The verl driver is the most complex. Key details:

- **Config**: Loads verl defaults via `hydra.compose("ppo_trainer")`, merges fm-tune overrides via `OmegaConf.merge()`. Must call `OmegaConf.set_struct(cfg, False)` first.
- **Overrides live in a pure module**: `autotune/trainers/verl_overrides.py::build_verl_overrides` maps a trial's sampled values to verl keys and returns a plain dict; `build_verl_config` only merges it onto verl's defaults. `rollout_n`, `rollout_temperature`, `kl_coef` and DAPO's `overlong_*` fall back from the sampled `train_kwargs` to the fixed `training_rl_config` via `_pick`; `learning_rate`, batch size, `clip_range` and entropy come from `train_kwargs` only, so keep them in the search space. It imports no torch/verl/hydra/omegaconf, so `tests/test_verl_overrides.py` runs on macOS and fails when a param in the `autotune.yaml` online-RL search space isn't wired (or listed as pending).
- **Colocated GPU pools**: Actor, critic, ref, and vLLM rollout share the same GPUs.
- **Memory optimizations**: `gpu_memory_utilization=0.3`, `enable_sleep_mode=True`, `free_cache_engine=True`, ref model `param_offload=True`, gradient checkpointing always on.
- **Hybrid (Mamba/SSM) bases**: no special case in the verl path. vLLM 0.24 captures full CUDA graphs for `GraniteMoeHybridForCausalLM` (Granite 4.0-H micro/tiny GRPO trained with `enforce_eager=False`); `enforce_eager` is set only for TP > 1. A detection block that forced eager mode had been commented out and was removed.
- **Workers (verl 0.9)**: the driver builds the v0 `RayPPOTrainer` (deprecated upstream in favour of `trainer.use_v1`) on the model-engine workers. It stays on v0 deliberately: V1 routes rollouts through TransferQueue, whose controller is a cluster-wide **named** Ray actor (`TransferQueueController`, namespace `transfer_queue`) that `tq.init()` attaches to if it exists, so concurrent RL HPO trials (`autotune.yaml` runs 8) would share one queue, mix rollout data, and the first trial's `tq.close()` would kill it under the others. `tests/test_verl_v0_trainer.py` fails if a verl bump removes v0, and flips when TransferQueue stops being a global singleton (the V1 port's precondition). The workers: `engine_workers.ActorRolloutRefWorker` hosts the reference policy (`Role.ActorRolloutRef`, or `Role.ActorRollout` when verl's `need_reference_policy()` says none is needed) and the PPO critic is a `TrainingWorker`. There is no separate ref worker or `RefPolicy` role.
- **Worker cleanup**: Must explicitly kill actors AND remove placement groups between HPO trials (`_verl_cleanup.cleanup_ray_resources`, see "verl Worker Cleanup").
- **LSF GPU mode**: verl runs vLLM in its own processes next to the FSDP workers, so RL jobs need `-gpu "num=N:mode=shared:j_exclusive=yes"`. The driver refuses to start under `exclusive_process`; `mode=shared` alone lets LSF put another job on the same GPUs (one smoke job found 74.8 GiB of GPU 0 held by a foreign process and OOMed at init).
- **Reward model**: Must set `reward.reward_model.rollout.name = "vllm"` (mandatory `???` field in verl YAML).

### Key Gotchas

Each entry has a one-line symptom and the fix.

- **Ray Train v2 metrics**: `Result.metrics` is only populated from checkpoint-attached `train.report()` calls (via `RayTrainReportCallback.on_save()`). Standalone `train.report(metrics)` is ignored by `CheckpointManager`. Fix: HPO uses `save_strategy="epoch"` + `save_total_limit=1` so `on_save()` fires at least once.
- **DeepSpeed "auto" scheduler**: The `"auto"` scheduler params in DeepSpeed config break TRL's `prepare_deepspeed()` for DPO/KTO ref model. Fix: omit the `scheduler` block from the DeepSpeed config in TRL drivers (HF Trainer manages the LR scheduler).
- **vLLM max_model_len**: If not set, defaults to model's `max_position_embeddings` (can be 128K+), causing OOM. Always set to `max_prompt_length + max_response_length`.
- **vLLM hybrid models**: older vLLM releases could not CUDA-graph-capture `GraniteMoeHybridForCausalLM` and other Mamba/SSM/RWKV architectures and needed `enforce_eager=True`; vLLM 0.24 does capture them (verified on Granite 4.0-H micro and tiny). Training-side, transformers 5.9 resolves the Mamba ops through `integrations.hub_kernels.lazy_load_kernel`: with the `kernels` package absent it imports a locally installed `mamba_ssm` / `causal_conv1d`, else it logs `The fast path is not available ... Falling back to the naive implementation` and runs a pure-torch scan that is several times slower and far hungrier (a 2-GPU Granite 4.0-H SFT smoke took ~22 min vs ~8 for a 3B MoE; KTO on 1 GPU ran out of memory at 80 GB in backward). `full` therefore pins `mamba-ssm==2.3.1` and `causal-conv1d==1.7.0`, compiled at install time like flash-attn (their `setup.py` hard-code sm75-sm121 on CUDA 13, so the compile is longer). Exactly 2.3.1: 2.2.x's top-level `import mamba_ssm` pulls `GreedySearchDecoderOnlyOutput`, which transformers 5 removed, and since transformers imports that top-level module the failure is silent (back to the naive path); 2.3.2 adds `tilelang` / `apache-tvm-ffi` / `quack-kernels` runtime deps.
- **verl placement groups**: Survive actor death. Must call `ray.util.remove_placement_group()` explicitly between trials — see "verl Worker Cleanup" below.
- **verl reward model `rollout.name`**: verl's default `reward/reward.yaml` has `name: ???` (OmegaConf mandatory). Must set `reward.reward_model.rollout.name = "vllm"` explicitly along with `tensor_model_parallel_size`, `enforce_eager`, `gpu_memory_utilization`, `max_model_len`, `enable_sleep_mode`, `free_cache_engine`.
- **DAPO overlong penalty location**: verl's (0.7.1 and 0.9.1) `"dapo"` reward manager (both the legacy and the reward-loop one) reads `reward.reward_kwargs.overlong_buffer_cfg` **and** `reward.reward_kwargs.max_resp_len`, and asserts `max_resp_len >= overlong_buffer_cfg.len`. Nothing reads `algorithm.overlong_buffer_cfg`. `build_verl_overrides` writes both keys and raises a `ValueError` if `overlong_buffer_len` exceeds `max_response_length`. Don't sweep `overlong_*`: the penalty is added to `critic/score/mean`, which is the HPO loss, so a sweep ranks trials on differently shaped rewards and favours the weakest penalty. They live in `training_rl_config` (guarded by `tests/test_verl_overrides.py`).
- **verl PPO clip bounds**: verl's (0.7.1 and 0.9.1) policy loss clips with `actor.clip_ratio_low` / `clip_ratio_high` (both default `0.2`) and falls back to `clip_ratio` only when they are `None`, so writing `clip_ratio` alone does nothing. `build_verl_overrides` writes all three from `clip_range`.
- **HF `load_best_model_at_end` requirements**: When set to `True`, requires `eval_strategy == save_strategy`, `save_steps % eval_steps == 0` (if `"steps"`), `metric_for_best_model` (e.g. `"eval_loss"`), and `greater_is_better` (`False` for loss). `trainer.save_model()` then saves the best checkpoint, not the last. The two multi-GPU HF drivers used to hardcode `load_best_model_at_end=False` and persist the *last* step's weights — silently shipping an overfitted model whenever eval loss turned back up before the final epoch. All three now go through `_checkpointing.resolve_checkpoint_strategy`; FSDP gathers via `fsdp_state_dict_type=FULL_STATE_DICT` and ZeRO-3 via `gather_16bit_weights_on_model_save=True`, so reloading the best checkpoint is a valid collective on every rank.
- **Ranks disagreeing on the best checkpoint crash the end of a multi-GPU run**: `ValueError: Can't find a valid checkpoint at .../checkpoint-74` from `_load_best_model`, on one rank only, after training finished. HF's `_save_checkpoint` sets `state.best_model_checkpoint` on each rank independently, gated on that rank's own `os.path.exists(best_checkpoint_dir)`, but `save_total_limit` rotation runs on rank 0 and protects only rank 0's best. Seen on 2-rank KTO + ZeRO-3 (rank 0: checkpoint-111, rank 1: checkpoint-74; the same job passed twice before). Fix: `autotune/callbacks/sync_best_checkpoint.py::SyncBestCheckpointCallback` broadcasts rank 0's `best_model_checkpoint` / `best_metric` / `best_global_step` after every save; all four multi-GPU drivers register it (`tests/test_sync_best_checkpoint.py` runs a real 2-rank gloo group).
- **`max_steps` from micro-batches trained every multi-GPU job `gradient_accumulation_steps` times too long**: all four multi-GPU drivers computed `steps_per_epoch = train_ds_size // (batch_size * num_workers)` — a *micro-batch* count — and passed `max_steps=steps_per_epoch * num_train_epochs`. HF counts every step-valued `TrainingArguments` knob (`max_steps`, `logging_steps`, `save_steps`/`eval_steps`, `torch_empty_cache_steps`) in **optimizer** steps, deriving its own as `len(train_dataloader) // gradient_accumulation_steps`, and `max_steps` silently overrides `num_train_epochs`. So a config asking for 2 epochs at `gradient_accumulation_steps: 4` ran 8 — observed on all four SR smoke jobs as a final `epoch` of 7.97/7.97/7.87/3.98 against `num_train_epochs: 2` (the last has `grad_accum: 2`). The fingerprint to look for in a log is a single line pair: `Dataset: 1833 train samples, 458 steps/epoch, 2 workers, batch_size=2` followed by a `697/916 [1:45:44<47:41` progress bar — `458 == 1833 // (2 * 2)` is the micro-batch count and `916 == 458 * 2` epochs, where the correct schedule is `114 * 2 = 228`. Three things kept it invisible: the logged `epoch` climbing past the configured value looks like rounding; `utils.assert_dp_sharding` compared HF's `max_steps` against the driver's own `steps_per_epoch * epochs` product, reproducing the error instead of catching it; and the Ray Data sample cap (`samples_per_rank`) was computed the same blind way, so it stayed self-consistent. The damaging part is not the wasted GPU time but the **HPO/final asymmetry**: HPO trials run `driver_single`, which sets no `max_steps` and honoured `num_train_epochs` exactly, so hyperparameters were selected under a schedule `grad_accum` times shorter than the final training they were chosen for. Also silently coarsened the single-epoch save/eval cadence (`steps_per_epoch // 5`), collapsing the five best-model candidates to one. Fix: `autotune/trainers/_steps.py::resolve_epoch_steps` owns the math for all five drivers and returns both counts (`optimizer_steps` for HF's knobs, `micro_batches` for a dataloader sample budget); change it there, not per driver. `assert_dp_sharding` now also derives HF's own `len(train_dataloader) // grad_accum` and warns when it disagrees with the driver by more than 1 (one batch of slack for `DistributedSampler` padding) — that is the check with teeth, since the drivers set `max_steps` themselves. `tests/test_epoch_steps.py` pins the arithmetic against HF's formula and greps the drivers for the old inline expression.
- **SFT batches were padded to `max_length`**: `tokenize_batch_arrays` left-pads every row to `max_length` and the drivers stacked rows as-is (`default_data_collator`), so every micro-batch ran `B × max_length` tokens through every projection, MLP and the LM head, however short its rows were. `flash_attention_2` already skipped pads *inside attention*, which hid it; the linear layers never did. Fix: `autotune/trainers/_collate.py` is the single collate seam for all three SFT drivers. The stored rows, the tokenizer and the **row count are unchanged**, so `resolve_epoch_steps`, `max_steps` and the Ray Data sample cap are untouched. `resolve_padding_mode` reads `padding_free: auto|true|false`. `auto` picks **padding-free** (`FlatteningCollator` → HF `DataCollatorWithFlattening`: one `[1, ΣLᵢ]` varlen row per micro-batch, per-sequence `position_ids` + `cu_seq_lens`, zero pad tokens) only for flash attention on CUDA, and never for SR, aLoRA (per-row invocation offset) or hybrid/Mamba/SSM bases (recurrent state would cross sequence boundaries). Otherwise it picks **dynamic** (`DynamicPadCollator`: rows are right-aligned, so one slice keeps `round_up(longest, 8)` columns; same loss) with length grouping (`group_by_length`, default on, dynamic mode only). `true` raises on a blocker instead of degrading. Length grouping uses `LengthGroupedTrainer`, whose sampler takes stored lengths (the Arrow file's `length` column; HF's own path would measure `max_length` for every row) and an **explicitly seeded generator**: every rank iterates the same sampler and `BatchSamplerShard` keeps every `world_size`-th batch, so the ranks must agree on the permutation. On `ray_data` the equivalent is `RayShardIterableDataset(group_by_length=True)` (sort within a buffer, shuffle runs). Trap: `label_names` must be `["labels"]`. The drivers used `["input_ids", "attention_mask"]`, and the flattened batch has no `attention_mask`, so `prediction_step` would see `has_labels=False`, return no loss, and `eval_loss` (what `load_best_model_at_end` selects on) would vanish. `tests/test_collate.py` pins both collators, the gating, rank-consistent sampling and the driver wiring.
- **PEFT adapter load races GPU 0 across ranks**: Under `-gpu mode=exclusive_process`, PEFT resolves its load device via `infer_device()`, which returns a bare `"cuda"` (i.e. `cuda:0`) and is **not** rank-aware. Ray Train gives every worker the full `CUDA_VISIBLE_DEVICES`, so all ranks try to load the adapter onto physical GPU 0 and ranks 1..N-1 die with `CUDA error: CUDA-capable device(s) is/are busy or unavailable`. `Trainer.train()` loads an adapter in **two** places: `_load_from_checkpoint()` at the start (resume) and `_load_best_model()` at the *end* (whenever `load_best_model_at_end=True`), both via `model.load_adapter()` -> `load_peft_weights()` -> `safe_load_file(..., device=infer_device())`. Fix: scope `_resume.py::peft_adapter_load_on_cpu()` around the **whole** `trainer.train()` call in every multi-GPU driver — unconditionally, not gated on `resume_from_checkpoint`. Gating it on resume covers only the first load and lets the best-model load crash at the very end of an otherwise successful run, after all the compute is spent. Single-GPU drivers are exempt (one process, one GPU, no contention).
- **Ray temp dir on a shared `/tmp`**: A path like `/tmp/_ray/job_<id>` has a *shared intermediate directory* — whichever user first creates `/tmp/_ray` owns it at their umask, and every other user then gets `PermissionError: [Errno 13]` beneath it, permanently, for that node. Seen in the wild as `drwxrwxr-x otheruser otheruser /tmp/_ray` while `/tmp` itself was a healthy `drwxrwxrwt`; jobs failed or succeeded purely on which node the scheduler picked. `exist_ok=True` does not help — it suppresses "already exists", not an unwritable parent. Fix: `autotune/tmpdir.py::resolve_ray_temp_dir` puts the **uid** in the parent (`/tmp/_ray-<uid>/...`, chmod'd to `0700`), prefers the scheduler's `TMPDIR`/`SLURM_TMPDIR` (LSF, Slurm, PBS and containers all set one), derives the job id from `AUTOTUNE_JOB_ID`/`LSB_JOBID`/`SLURM_JOB_ID`/`PBS_JOBID`/`JOB_ID` then the pid (`LSB_JOBID` alone collapsed to a shared `"0"` off-LSF), and falls back through the candidate list instead of dying. Two subtleties: `tempfile.gettempdir()` itself honours `TMPDIR`, so a hardcoded `/tmp` candidate is needed or a poisoned `TMPDIR` leaves no fallback at all; and `os.makedirs(mode=...)` sets the mode on the **leaf only** (and umask-masked), so the per-uid parent needs an explicit `chmod`. Paths are length-capped (`MAX_TEMP_DIR_LEN = 42`) because Ray puts the plasma `AF_UNIX` socket underneath (up to 65 more bytes: `session_<timestamp>_<7-digit pid>/sockets/plasma_store`) and `sun_path` holds 107 characters plus the NUL — a too-long dir fails inside Ray far more confusingly. The cap used to be 44, which an LSF worker suffix (`w_<job>_<host>_<pid>`) overflowed by one byte; an over-long *suffix* is now shortened to a prefix plus 8 hex chars of its SHA-1 (`_fit_suffix`, deterministic) instead of being rejected on every candidate root. Override with `FMTUNE_RAY_TMPDIR`. All four Ray temp dirs (`cluster.py`, `lsf/ray_up.py`, `lsf/ray_up_blaunch.py`, `lsf/worker_entry.py`) route through it.
- **Ray Data + pandas 3.x**: Pandas 3.0 removed `SettingWithCopyWarning`; Ray Data 2.54's pandas `BlockAccessor` still referenced it, so any `map_batches(..., batch_format="pandas")` crashed. Ray 2.59 (the current pin) guards the lookup with `hasattr`, but the drivers keep `batch_format="numpy"` (the default) and convert inside the UDF, which is also what `batch_to_dataframe` assumes (see the chat-format gotcha below) — don't switch back to pandas batches.
- **Ray Data object-store sizing**: Client-side `ray.init(object_store_memory=...)` does NOT resize an existing remote cluster's object store. Size it on cluster bringup (`--object-store-memory` to `ray start`, or `RAY_DEFAULT_OBJECT_STORE_MEMORY_PROPORTION=0.5` before `ray start`). Local clusters: `autotune/cluster.py::start_local_ray_cluster` already sets 0.5.
- **FSDP NO_SHARD warnings**: Small models on colocated pools may fall back to `NO_SHARD` and emit warnings. Benign *as a fit signal* — the model fits per-GPU without sharding — but see the next entry: a `NO_SHARD` fallback caused by `world_size == 1` is **not** benign on this driver.
- **FSDP `NO_SHARD` + `use_orig_params=True` cannot write back**: a 1-worker run dies on the *first* training step with `RuntimeError: Cannot writeback when the parameter shape changes / Expects torch.Size([81920]) but got torch.Size([32, 2560])`. FSDP refuses to shard across one rank (`FSDP is switching to use NO_SHARD instead of ShardingStrategy.FULL_SHARD since the world size is 1`), and in `NO_SHARD` torch's `_FlatParamHandle._writeback_orig_params` (`torch/distributed/fsdp/_flat_param.py`) skips its early return — that one is gated on `uses_sharded_strategy`, which `NO_SHARD` is not — yet still computes `expected_shape = torch.Size([numel_in_shard])`, a **1-D** shape, while `fsdp_use_orig_params=True` (which `_build_fsdp_config` always sets) keeps every parameter registered at its logical shape. So the first parameter needing writeback raises unconditionally. Genuinely-sharded runs are unaffected: they take the `is_sharded` path and compare against a real 1-D shard view. The 2-D shape in the message is a `lora_A.weight` inside an FSDP-wrapped LoRA submodule, which makes this look PEFT- or SR-specific — it is neither. Fix: `_build_fsdp_config(strategy, num_workers)` returns `("", {})` when `num_workers <= 1`, the same no-FSDP return the `no_shard` branch already produced, so nothing downstream is new and the run is strictly cheaper. This bites SR hardest because `fit_best_config` sets `multi_gpu = accel.supports_distributed` (`True` on any CUDA box), so a **1-GPU** SR run sends its *final* training to the FSDP driver with `num_workers=1` — both the `--no_autotune` and the HPO variants crashed there while their HPO trials on `driver_single` trained fine.
- **A crashed final-training trial used to exit 0**: `fit_best_config()` returns Ray Tune's `ResultGrid`, and Tune reports a crashed trial *inside* that grid instead of raising — so `result_grid.get_best_result()` returned the errored trial with empty metrics, `main.py` logged `[AutoTune] Done (exit code 0).`, and LSF said `Successfully completed.` for a run that saved no model at all. Fix: `main.py` raises on `result_grid.num_errors` before reading the best result, which is what the comment there always claimed happened ("a run failure still propagates to the build via the non-zero process exit code"). Consequence for verification: never treat an exit code or an LSF status as a pass signal for a training run — check for the saved weights.
- **PEFT 0.21 saves empty adapters under multi-rank FSDP**: `adapter_model.safetensors` is a valid 512-byte file with **zero tensors**, no error anywhere, and the run "passes". PEFT 0.21.0 rebuilt `get_peft_model_state_dict` on prefixes from `model.named_modules()` and strips `_fsdp_wrapped_module.` only when it is *leading*; `TRANSFORMER_BASED_WRAP` wraps each decoder layer, so the segment sits mid-path (`...layers.0._fsdp_wrapped_module.self_attn...`) and nothing matches the gathered (clean) keys. 0.21.2 is still affected. Fix: pin `peft==0.19.1` (also shadow-residual's pin). Verification consequence: check a saved adapter by **tensor count**, not file size.
- **torch 2.11 cuDNN SDPA returns NaN gradients on left-padded batches**: with `attn_implementation="sdpa"` on H100, step 0 logs a finite loss with `grad_norm=nan` and every later step is `nan`. The cuDNN backend's backward mishandles fully masked query rows, which every left-padded batch has. Forward is fine, so eval-only paths never show it; `flash_attention_2` and `eager` are unaffected (which is why the default configs passed and Shadow Residual, whose configs default to `sdpa`, did not). Fix: `device.disable_cudnn_sdpa()` at each driver's worker entry (`tests/test_cudnn_sdpa_guard.py` pins all six); SDPA then uses its flash / memory-efficient kernels.
- **RL trial logs silenced by a vLLM dependency**: an RL run trains and saves, but nothing fm-tune logs after `init_workers()` appears (no `[AutoTune] verl step N` lines, results, cleanup) while `print` output does. vLLM 0.24 pulls in `model_hosting_container_standards`, whose `configure_root_logger()` sets the root logger **and every root handler** to `$SAGEMAKER_CONTAINER_LOG_LEVEL`, default `ERROR`; verl imports it in the trial process. Fix: `driver_multi_verl.py` `setdefault`s the variable to `INFO`, and snapshots/restores root levels around `init_workers()`/`fit()` (which also undoes vLLM's `suppress_logging`, a `logging.disable(INFO)` without `try/finally`).
- **TRL DPO/KTO on FSDP never trained**: three independent faults, the first reproduced on the old torch 2.8 / TRL 0.29 stack too. (1) `AssertionError: Invalid: _post_backward_hook_state` on the first backward: TRL computes reference log-probs inside the training step by disabling the adapter under `no_grad`, and PEFT's `enable_adapters` flips `requires_grad` on the adapter weights between FSDP's forward (which registered the hook) and the backward. Fix: `_peft_fsdp.peft_adapter_toggle_keeps_requires_grad()` around `trainer.train()` makes a no-grad toggle flag-only. (`precompute_ref_log_probs=True` would avoid it, but TRL precomputes in `__init__`, before the FSDP wrap, when `fsdp_cpu_ram_efficient_loading` leaves ranks > 0 on meta weights.) (2) `AssertionError: Expects 163840 numel but got 81920` at the first checkpoint save: `fsdp_forward_prefetch` assumes a static module order, which the adapter-disabled reference pass breaks; off in the TRL FSDP driver. (3) No single-worker guard, so 1-GPU final training hit the world-size-1 `NO_SHARD` trap above; the HF FSDP driver's guard is now in the TRL one too.
- **trl is pinned at 1.12.0, not latest**: TRL 1.13 removed `trl.experimental.ppo`, and verl's PPO critic (`load_valuehead_model`) falls back to `AutoModelForCausalLMWithValueHead` because Granite has no `*ForTokenClassification` in transformers 5.9. Do not bump past 1.12 without replacing that fallback.
- **transformers 5 logs Trainer metrics as quoted strings**: `{'loss': '8.809', 'grad_norm': 'nan', ...}`. A regex like `'loss': *[0-9.]+` silently matches nothing, and `'loss': *nan` misses `'nan'`, which is how a NaN Shadow Residual run first "passed" a smoke check. In-memory `trainer.state.log_history` values are still floats.
- **GRPO length collapse**: within ~15 steps responses shrink from ~150 tokens to 2 (`#### N`), entropy goes to 0 and `critic/score/mean` settles near -0.95 — reproduced identically on verl 0.7.1 with the pre-upgrade code, so it was never an upgrade regression. Two things combined: the shipped `autotune/rewards/gsm8k_reward.py` subtracted a length penalty (up to 0.2, len/4000), and GRPO's `norm_adv_by_std_in_grpo=True` divides each group's advantages by its reward std — in a group whose answers are all right or all wrong, that std is a few hundredths and the division turns the length differences into +-1 advantages (shortest +1.24, longest -1.01 for an all-correct group of 300-900 chars). Shorter answers get more wrong, more groups become all-wrong, the loop runs away. Ablations: std normalization off -> ~100-token responses, score 0.6-0.97; length penalty off -> ~180 tokens, score up to 1.05. Fix: the reward has no length penalty, and `build_verl_overrides` sets `norm_adv_by_std_in_grpo` from `training_rl_config` (default **false**, mean-only "Dr. GRPO" centering). DAPO already ran without std normalization and never collapsed; PPO uses a critic.
- **`kl_coef` did nothing for GRPO/DAPO**: `use_kl_loss` was always `False` and `use_kl_in_reward` is `False` for every algorithm, so the swept `kl_coef` changed nothing and no term held the policy near the reference. Fix: for GRPO and DAPO, `kl_coef > 0` turns on `actor.use_kl_loss` with `kl_loss_coef = kl_coef` (verl's `low_var_kl`), which also makes verl load the reference policy (`Role.ActorRolloutRef`, `param_offload=True`); `kl_coef == 0` (DAPO's default) keeps it off. PPO's handling is unchanged.
- **TRL DPO/KTO crash on Granite MoE and 4.0-H bases**: `AttributeError: 'int' object has no attribute 'mean'` (1 GPU) or `TypeError: 'int' object is not iterable` (multi-rank gather) on the first step. TRL treats any config with an `output_router_logits` attribute as MoE and, at its default `router_aux_loss_coef=0.001`, logs `gather_for_metrics(outputs.aux_loss).mean()`. In transformers 5.9 the Granite MoE classes (`GraniteMoeForCausalLM`, `GraniteMoeHybridForCausalLM`) register no `router_logits` output recorder (Mixtral does), so `outputs.router_logits` is `None` and `load_balancing_loss_func` returns the Python int `0` — including on Granite 4.0-H micro, which has **zero** experts. Consequence beyond TRL: on these classes the router load-balancing loss is silently 0 for every fm-tune run, SFT included. Fix: `autotune/trainers/_moe.py::router_aux_loss_coef(model)` returns `0.0` exactly when the class cannot record router logits (numerically a no-op there) and `None` otherwise, and the three TRL drivers pass it into `DPOConfig`/`KTOConfig`; a model or transformers release that does compute the loss keeps TRL's default. `tests/test_moe_aux_loss.py` pins it on the real classes.
- **PlacementGroupCleaner warnings**: `Failed to query Ray Train Controller actor state ...` from `ray.train.v2._internal.execution.controller.placement_group_cleaner` are benign State-API hiccups under load. Suppress by setting that logger to `ERROR`.
- **Granite `documents` differ by generation**: `apply_chat_template(..., documents=[...])` never raises when the template ignores the kwarg — it renders a valid prompt with the RAG context silently missing. Granite 3.x reads `document['doc_id']`/`['text']` (doc_id required); Granite 4.0/4.1 do `document | tojson` into a `<documents>` block with **verbatim keys** (so `doc_id` leaks into the prompt); **Granite 4.2 removed `documents` entirely** (moved to ChatML) — there the context goes in as a `{"role": "tool"}` message, which 4.2 renders as a `<tool_response>[...]</tool_response>` block (a JSON array of `{source, document_id, content}`); no assistant `tool_calls` turn and no `tools` schema are needed. Because that block is one JSON *array*, `build_documents` **merges all of a datapoint's contexts into a single document** (joined by `\n\n`) for `DOC_STYLE_TOOL`, so the 4.2 prompt matches the single `<documents>` block 4.1 renders instead of fragmenting into N array entries; the merge lives in `build_documents` (not `tool_documents_message`), so callers passing pre-built `{source, document_id, content}` records keep one entry each. For judge/guardian data the tool message is placed **before the first assistant turn** (the docs ground the response being judged; after the last user turn would bury them after the instruction, just before the label). `model_type` is `granite` for both 4.1 and 4.2, so detect via `tokenizer.chat_template` introspection, not model names — the ChatML check (`<|im_start|>`, template text then vocab membership; never `convert_tokens_to_ids`, whose unk id false-positives) must run **before** the `doc_id`/`document` substring checks or a 4.2 template mentioning either word silently falls through to the native path. The SFT drivers forward the `documents` column blindly, so a 4.2 model + `documents` column trains on context-free prompts. Separately, **4.2 defaults to `enable_thinking=True`**, ending the prompt in an open `<think>` block — training a structured target (JSON verdict, NLI label, atom list) against that teaches the model to emit it as reasoning content; pass `enable_thinking=False` on templates that accept it. Fix: `autotune/tools/chat_utils.py` (`detect_document_style`, `attach_documents`, `render_chat_input`) picks the document shape per template — `DOC_STYLE_TOOL` for 4.2, `granite3`/`granite4` natively, `inline` (leading system message) for other templates that ignore the kwarg — and gates the thinking kwarg. `attach_documents` is the single seam shared by the dataset builders and the eval-side `_guardian_prompt`, so training and eval prompts cannot drift. `--doc-style` overrides detection; `--no-inline-documents` gates only `inline`, never `tool`. Shared by all three dataset builders (factuality/atomizer/nli), whose prompt texts (guardian/atomizer/NLI) live in the same module. The three SFT drivers render the template themselves for `chat`-format datasets, so they gate `enable_thinking` the same way (the shared `thinking_kwargs` / `apply_chat_template_to_df` in `autotune/tools/chat_utils.py`, override via `disable_thinking: false` in `training_config`) — otherwise a chat dataset on 4.2 trains its target inside an open `<think>` block. See `docs/dataset-sft.md`.
- **QLoRA (`--tuning_algo qlora`)**: LoRA on a 4-bit (NF4) bitsandbytes-quantized base. Maps to `PeftType.LORA` (`constants.py`) — same tunable surface as `lora`; the quantized load is triggered purely by `training_config["tuning_algorithm"] == "qlora"` inside the drivers. Drivers build the 4-bit `BitsAndBytesConfig` via `utils.get_qlora_quantization_config()` and call `utils.prepare_qlora_model()` before adapter attachment (HF drivers before `get_peft_model`; TRL drivers before handing the model to the trainer, since TRL's `DPOTrainer` does *not* auto-run `prepare_model_for_kbit_training`, only KTO does). **Incompatible with DeepSpeed ZeRO-3 and FSDP `full_shard`** — the quantized 4-bit params can't be sharded by ZeRO-3 sharded-init / FSDP flat-param sharding; those combos raise a clear `ValueError`. Use ZeRO-1/ZeRO-2, FSDP `SHARD_GRAD_OP`, or the single-GPU driver.
- **Ray object store capped on non-CUDA**: The CUDA path sizes the local Ray object store via `RAY_DEFAULT_OBJECT_STORE_MEMORY_PROPORTION=0.5` (50% of RAM), which would reserve 8 GB on a 16 GB Mac and starve Metal. Fix: on non-CUDA, `autotune/device.py::object_store_bytes()` sizes the object store to a fixed 2 GiB (`2147483648`) instead, overridable via `FMTUNE_OBJECT_STORE_BYTES` (bytes).
- **Trial log attribution under concurrency**: `BufferedLogHandler.emit()` used to stamp every record with the handler's single mutable `self.trial_id`, which `CustomLoggerCallback` overwrote per Tune event. In the driver process *all* trials' output converges on that one root-logger handler — Ray runs `log_to_driver=True`, so worker stdout is forwarded into the driver, where `main.py` swaps `sys.stdout` for `PrintLogger` -> `logging`, and those lines arrive on Ray's log-forwarding *thread*, racing the Tune control thread. Result: trial A's logs stored under trial B. Fix: attribution is per-record — an explicit `extra={"trial_id": ...}`, else a `contextvars` id set by `logging_service.trial_context()` (used by the Tune callbacks, so a callback claims only its own records), else the handler default. The handler default is set **only in worker processes** via `logging_setup.bind_trial_id()`, which every driver calls once it knows its trial: one worker process serves one trial, so it can label at the source for every thread (HF Trainer, dataloaders). Never set a process-wide trial id in the driver. `logging_setup.bridge_runtime_env()` ships `AUTOTUNE_JOB_ID`/`AUTOTUNE_ENDPOINT_URL` to workers as a job-level Ray `runtime_env` so off-node workers can build their own handler (they don't inherit the driver's environ); it returns `{}` when the bridge is off, leaving `ray.init()` untouched by default. Related: `flush()` now detaches the buffer under the lock before the blocking send, so records emitted mid-POST aren't discarded by the post-send reset and a slow endpoint doesn't stall every thread that logs.
- **Shadow Residual (`--tuning_algo sr`)**: A dual-stream Granite decoder — a frozen base stream that stays bit-exact with the unadapted base, plus a trainable adapter stream fed by stock LoRA deltas and a per-layer rank-`cross_stream_r` injection from the base. Only `norm(h_adapt)` reaches the LM head; hidden states are carried as a stacked `[2,B,S,H]` tensor. It is **100% stock PEFT LoRA** — no custom `LoraLayer`, no `PeftType`. `CrossStream` is a real frozen zero-init `nn.Linear(H,H)` that ordinary `peft.tuners.lora.layer.Linear` wraps, so the site yields a pure rank-R `B·A·scaling` injection, and `"cross_stream"` in `target_modules` is what *engages* the dual-stream forward (absent it, a single-stream early-exit path runs). Everything SR-specific lives in `autotune/shadow_residual.py`; the drivers stay thin. **Install:** `git clone https://github.com/generative-computing/shadow-residual && pip install -e shadow-residual --no-deps` — fm-tune imports `shadow_residual` lazily (`require_sr()` raises an `ImportError` naming that exact command), so the dependency stays optional and no fm-tune pin moves (SR's own metadata wants `transformers>=5.5.1`/`peft==0.19.1`, which is a metadata conflict only).
  Six things that are load-bearing and non-obvious:
  - **`peft_type` is the bare string `"SR"`** (`AUTOTUNE_TUNING_TO_PEFT_TYPE`), the same escape hatch as `"alora": "ALORA"`, and `get_peft_config` maps it back to a plain `LoraConfig`. `get_peft_config` ends in `else: peft_config = None  # SFT`, so **a missing branch there degrades an SR run to a silent full fine-tune with no error anywhere** — the symptom is a `trainable params: …` line near 100%. `tests/test_sr.py` pins the branch.
  - **`alpha_ratio` is `for_tuner: true` for `sr` and `false` for every other tuner.** The drivers compute `lora_alpha = alpha_ratio * peft_kwargs["r"]`, but SR's `r` is the *minimum* rank (PEFT's scalar default, with per-name overrides in `rank_pattern`), so that would scale from the min instead of SR's `2 × max_rank`. `for_tuner: true` routes it into `peft_kwargs`, leaving the drivers' `train_kwargs.pop("alpha_ratio")` at `None`, and `build_sr_lora_config` computes it from `max(r, cross_stream_r)`.
  - **`rank_pattern` names *every* target, not just `cross_stream`.** With `r = min(...)`, a target missing from `rank_pattern` silently trains at the minimum rank rather than the sampled one whenever `cross_stream_r < r`.
  - **The FSDP driver must build `TrainingArguments` *before* the model.** `TrainingArguments.__post_init__` sets `os.environ["ACCELERATE_USE_FSDP"] = "true"` when `len(self.fsdp) > 0`, and SR's factory reads that env var (plus `LOCAL_RANK`, set by Ray Train's `_set_torch_distributed_env_vars`) to decide that only rank 0 materializes real CPU weights while the other ranks stay on meta until `fsdp_sync_module_states` broadcasts. Moving the `TrainingArguments` construction later would silently make every rank materialize a full CPU copy of the base. Nothing ever *clears* that env var either, so `build_sr_peft_model` takes an explicit `fsdp_active` kwarg rather than trusting the environment.
  - **`auto` is forced to `full_shard`; every explicit strategy including `no_shard` passes through** (`resolve_fsdp_strategy`). `auto` is overridden because `_estimate_memory_components` sizes trainable params from a single-stream LoRA assumption — it ignores `rank_pattern`, counts the K/V sites SR forbids, and omits the per-layer frozen `CrossStream` linears — and would answer `no_shard` on a 3B. `no_shard` used to be rejected too, on two grounds that do not survive inspection. First, fm-tune's `no_shard` is **not** torch's `ShardingStrategy.NO_SHARD` (the one broken against `fsdp_use_orig_params`, see the gotcha above) — `_build_fsdp_config` returns `("", {})` for it, so there is no FSDP wrap at all and Accelerate wraps in plain **DDP**. With `ACCELERATE_USE_FSDP` unset, SR's factory materializes on *every* rank (`local_rank == 0 or not fsdp_active`), so no rank is left on meta and `.to(device)` is valid; this is upstream shadow-residual's own documented multi-GPU recipe, and it is literally the code path a 1-GPU SR final training already takes. Second, the per-rank `reset_lora_parameters` divergence is real before the wrap but repaired unconditionally after it: `DistributedDataParallel.__init__` calls `torch.distributed.utils._sync_module_states`, which broadcasts every `named_parameters()` entry from rank 0 (gated only on `init_sync`, default `True`, and not exposed by `accelerate`'s `DistributedDataParallelKwargs`) — the same mechanism the plain-LoRA `no_shard` path has always relied on. RoPE `inv_freq` is recomputed identically per rank, so `ddp_broadcast_buffers=False` stays safe. What remains is a capacity fact, not a correctness one, so it is a `logger.warning`: host RAM scales with ranks **per node** rather than one copy per node (~2× the base's bf16 size at peak, ~12-14 GB on a 3B), because there is no `fsdp_cpu_ram_efficient_loading` to hold it to one. Verified on a 2-rank gloo/CPU harness: no meta leftovers, `lora_A` identical after the DDP wrap, no divergent buffers, finite loss with gradient checkpointing, and bit-identical weights across ranks after two optimizer steps. Relatedly, `train_loop_per_worker` now calls `set_seed(seed)` before it builds anything — the driver's `set_seed` runs in the trial process and HF's `Trainer.__init__` seeds only after the model exists, so adapter init was unseeded on every rank; the wrappers repaired it, but now the ranks agree by construction and a run is reproducible from its seed.
  - **Rejections are hard, not fallthroughs, because the failure is silent.** PEFT's `inject_adapter` raises only when *nothing* in `target_modules` matched, so on a plain Granite base the `cross_stream` target is dropped without a warning and the run trains as ordinary LoRA while being reported as `sr`. Hence the explicit raises for DeepSpeed and the three TRL drivers, for MoE bases (`ShadowResidualMLP` builds `gate/up/down_proj` only on the dense branch — three of six targets would vanish), for hybrid/non-attention bases, for non-Granite bases, for RL, and for MPS/MLX. `main.py` guards too, before Ray starts: a driver-level raise only ERRORs the Ray trial, so an HPO sweep would burn its whole budget producing N identical failures.
  Two more operational notes: **host RAM, not GPU, is the binding constraint** — SR always materializes on CPU first (~12-14 GB peak per materializing process on a 3B base: the SR model plus the transient upstream `from_pretrained` copy that `transfer_base_weights(..., drain_src=True)` frees incrementally), and HPO trials run `max_concurrent_trials` of those at once. And **a step-1 `nan` is the meta-materialize signature** — `to_empty(cpu)` leaves garbage in anything neither the weight transfer nor the LoRA reset repopulates (`CrossStream` weights, non-persistent RoPE `inv_freq`); re-run with `SR_DIAG_MATERIALIZE=1` for SR's per-tensor finite/zero audit. Configs: `autotune/configs/autotune_sr_3b.yaml`, `autotune/configs/autotune_sr_smoke_1gpu.yaml`, `autotune/configs/autotune_sr_smoke_2gpu.yaml`. Prefer the **2-GPU** smoke for routine re-verification: `num_workers=2` is the smallest world size that builds an `fsdp_config` at all (`_build_fsdp_config` returns `("", {})` at `num_workers <= 1`), so it is the cheapest config that reaches the `TRANSFORMER_BASED_WRAP` class lookup and a real multi-rank `sync_module_states` broadcast — the 1-GPU smoke never shards. When checking their results, an exit code of 0 is not a pass signal: it does not distinguish SR from the plain-LoRA and full-fine-tune degradations above.
- **Silent MPS CPU fallback**: `PYTORCH_ENABLE_MPS_FALLBACK` defaults to `"1"` (set by `configure_runtime_env` on non-CUDA), so an op with no MPS kernel silently runs on CPU instead of crashing — a real slowdown that's easy to miss. Fix: set `PYTORCH_ENABLE_MPS_FALLBACK=0` to make PyTorch raise instead, which pinpoints exactly which op lacks a Metal kernel.
- **`trust_remote_code` opt-out**: Every HF `from_pretrained` (model/tokenizer/config) call passes `trust_remote_code=` via `utils.resolve_trust_remote_code()`, which defaults to `True` — Granite hybrid and some custom architectures ship modeling code in the model repo, so loading executes that Python by default. Operators who only load architectures bundled with `transformers` can harden this by setting `FMTUNE_TRUST_REMOTE_CODE=0` (also accepts `false`/`no`/`off`). It's a single centralized knob; don't re-hardcode `trust_remote_code=True` at new call sites — call the helper.

|---------|----------|--------|

| Reference (inference) | ~1.7 GB | — | ~1.7 GB |
| vLLM rollout (inference + KV) | ~1.7 GB + KV | — | varies with `gpu_memory_utilization` |

Top wins (in order): drop `gpu_memory_utilization` 0.5→0.3 (~16 GB/GPU), `enable_sleep_mode + free_cache_engine` (~6.6 GB), gradient checkpointing on (~2–4 GB), ref `param_offload=True` (~1.7 GB).

## verl Worker Cleanup

`RayPPOTrainer` has no shutdown method. Between HPO trials, both worker actors AND placement groups must be torn down explicitly — killing actors alone leaves placement groups holding GPU reservations and the next trial fails with `Total available GPUs 0 is less than total desired GPUs N`.

verl 0.9 also starts actors *outside* the worker groups (the vLLM servers behind `llm_server_manager`, `reward_loop_manager`'s `RewardLoopWorker`s, `async_rollout_manager`'s `AgentLoopWorker`s), none with a shutdown method and with attribute names that change between releases. So `autotune/trainers/_verl_cleanup.py::cleanup_ray_resources(trainer)`, called from the `finally` around `trainer.fit()`, walks the trainer's object graph (depth-bounded, cycle-safe, skipping torch/omegaconf/dataset internals) and kills every reachable `ActorHandle` and removes every reachable `PlacementGroup` — 21 actors and 1 placement group per 2-GPU trial on verl 0.9.1. It deliberately touches nothing *not* reachable from this trainer: concurrent HPO trials share one Ray job, so a "kill every actor in the job" sweep would take down sibling trials. `tests/test_verl_cleanup.py` pins it with stand-ins shaped like 0.9.1's trainer.

## Multi-node Ray clusters (LSF / Slurm)

`--scheduler {lsf,slurm}` (default `lsf`) picks who owns the multi-node allocation. Both paths are one allocation of `--num_nodes` hosts: `ray start --head` (CPU-only) plus a colocated worker on host[0], one worker per other host, each registering `--gpus_per_node` GPUs; `python -m autotune.lsf.worker_entry` (with its GPU-count guard) is the worker on both.

- **LSF** (`autotune/lsf/ray_up_blaunch.py`): runs only when `--conda_env` is given (else a local single-node cluster). Hosts from `LSB_DJOB_HOSTFILE`/`LSB_HOSTS`; remote workers via `blaunch -z host bash -lc "conda activate ..."`. Teardown needs a remote `ray stop` via blaunch and a closing self-`bkill`, because LSF won't reap the job while its cgroup holds processes.
- **Slurm** (`autotune/slurm/ray_up_srun.py`, submit with `sbatch -N N --gres=gpu:G --exclusive --mem=0`): always runs with `--scheduler slurm`; `--conda_env` is ignored. Hosts from `SLURM_JOB_NODELIST` (`scontrol show hostnames`, with a pure-Python expander as fallback); `num_nodes` must equal the node count. Each remote worker is its own `srun --nodes=1 --nodelist=host --overlap --mpi=none --mem=0 --cpus-per-task=<host CPUs> sys.executable -m ...` step. Four traps: (1) a step gets **one CPU** unless `--cpus-per-task` is given (task/cgroup would pin the raylet and every Ray worker on that node to one core), so the count is parsed per host from `SLURM_JOB_CPUS_PER_NODE` (`96(x2)`); (2) no `--gres` on the step, which inherits the job's GRES by default (naming it clashes with `--gpus` jobs), and the worker's GPU guard names the node if it ever gets fewer; (3) no shell or conda activation, since srun exports the driver's env (RDMA vars passed via `Popen(env=)`); (4) `--mpi=none`, because this cluster defaults to PMIx. Teardown (`autotune/slurm/ray_down.py`) is `ray.shutdown` → SIGTERM each worker's process group (srun forwards it to `worker_entry`, which runs `ray stop`; 30 s grace, then SIGKILL) → stop the head. No self-`scancel`: proctrack/cgroup reaps the steps when the batch step exits, so the job ends `COMPLETED` with main.py's exit code. Unlike LSF, a worker that dies during bring-up also triggers partial teardown. `--fleet bv-h200` selects the 8-rail H200 preset.

## Data Backend Selection (FSDP driver)

`driver_multi_hf_fsdp.py` selects between two dataset paths via `--data_backend` (default `arrow`):

- **`arrow`** — driver tokenizes once on the head node, writes `{output_dir}/data_cache/{trial_id}/*.arrow`, workers memory-map. HF Trainer's distributed sampler shards rows. Robust, bounded object-store pressure. Use when tokenization is cheap relative to training.
- **`ray_data`** — driver builds `ray.data.Dataset` (`read + repartition + map_batches` tokenize), passes to `TorchTrainer(datasets=...)`, workers consume via `train.get_dataset_shard()`. Tokenization scales across the cluster (all nodes), no Arrow file on disk. Requires cluster-side object-store sizing ≥50% of node RAM (see gotcha above), and `accelerator_config={"dispatch_batches": False}` on `TrainingArguments` to avoid a `SplitCoordinator` deadlock under Accelerate's iterable-dataset dispatch path. Emits a one-time ~30 s `StreamSplit` warning on the first pull. Use when tokenization dominates startup or the dataset is too large to tokenize serially. Both `driver_multi_hf_fsdp.py` and `driver_multi_hf_ds.py` share this path. Concurrency controls (sizing helpers live in `autotune/cluster.py`):
  - **Tokenize once, before the GPUs start (`autotune/trainers/_ray_data.py::build_tokenized_datasets`, shared by both drivers).** The trainer needs the *tokenized* row count for `max_steps` (the sliding window in `utils.tokenize_batch_arrays` expands long records, so the raw count is not it). The old pipeline got it from `count()` on a lazy dataset, which ran the whole tokenization on the head before the `TorchTrainer` existed, discarded it, then re-tokenized during training once per epoch. Now the raw text is read → subsampled → shuffled (seeded; the Arrow backend's `DistributedSampler` shuffles globally, a 4096-row local buffer alone does not) → repartitioned → **materialized**, and only then tokenized on a fixed `ActorPoolStrategy` pool (one tokenizer load per actor, `TOKENIZERS_PARALLELISM=false`) and materialized again. The intermediate materialize is load-bearing: the pool is sized to every free CPU and Ray Data reserves CPUs for it up front, so with the shuffle/repartition still upstream they got a CPU budget of 0 and the pipeline deadlocked (2 of 3 runs on a 4-CPU local cluster). Tokenized blocks hold only `input_ids` plus int32 `pad_len`/`target_len` (`compact_rows`); `RayShardIterableDataset` (shared by both drivers) rebuilds `attention_mask`/`labels` on the GPU worker (`expand_rows`) — 3× less object store than carrying all three. Never infer the mask from `input_ids == pad_token_id`: `get_tokenizer` defaults pad to EOS, which ends every target. `get_tokenizer` uses the fast tokenizer; `tests/test_tokenize_arrays.py` pins id-for-id parity against the old slow path.
  - **Chat-format rows arrive as numpy, not lists.** Under `batch_format="numpy"` a list-valued column (`messages`, `documents`, `tools`) reaches the UDF as an object array of `np.ndarray` of dicts. `apply_chat_template_to_df` detects chat rows with `isinstance(first, list)`, so a plain `pd.DataFrame(batch)` silently skipped the chat template and tokenized `str(ndarray)` as the prompt — every chat-format `ray_data` run trained on garbage prompts, no error. The Arrow backend was unaffected (pandas' `read_json` keeps lists). Fix: `TokenizeBatch` builds its frame with `_ray_data.batch_to_dataframe`, which converts nested cells back to lists/dicts; the slow `[chat]` case of `test_build_tokenized_datasets_matches_tokenize_batch` runs the real template end to end and fails on the old code.
  - **Repartition is the primary fan-out lever.** Ray Data hands each input *block* to one map task/actor, and a single source file usually reads as 1 block — so the driver calls `repartition(n, shuffle=False)` (a cheap split/combine, no full shuffle) to split train/eval into ≈`concurrency` blocks before `map_batches`. Block count is clamped to the dataset row count, so tiny eval sets aren't over-partitioned (skipped entirely when ≤1 row). Without this, tokenization runs single-CPU regardless of cluster size.
  - `ray_data_concurrency` (int): number of parallel `map_batches` tasks. **Default (auto) = `floor(available_cpus / ray_data_num_cpus)`** at tokenization time via `compute_ray_data_sizing()` — tokenization finishes, and its actors are released, before the trial's GPU workers are scheduled, and counting *available* CPUs excludes those held by sibling HPO trials. Override via the `--ray_data_concurrency` CLI flag or the YAML training-config key.
  - `ray_data_num_cpus` (float, default 1.0): logical CPU budget per tokenizer actor; fractional values (e.g. 0.5) allow more concurrent actors per physical CPU. Override via `--ray_data_num_cpus` or YAML.
  - **Concurrent HPO:** sizing counts *available* CPUs, so CPUs held by sibling trials' GPU workers are excluded, but two trials that start tokenizing at the same moment can both claim the same free CPUs. That's not a deadlock (actors provision asynchronously; the pool grows as CPUs free up), but for wide sweeps set `--ray_data_concurrency` explicitly for predictable startup. See `docs/RESOURCES.md`.
